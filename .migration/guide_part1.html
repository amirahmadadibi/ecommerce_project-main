۱) مقدمه: چه اتفاقی افتاد و چرا؟

تا این لحظه از دوره، بک‌اند اپلیکیشن Apple Shop روی PocketBase آدرس https://startflutter.ir/api/ اجرا می‌شد. PocketBase برای شروع یادگیری عالی است، اما این پروژه به یک بک‌اند Supabase سلف‌هاست (میزبانی‌شده روی Liara) منتقل شده است. این راهنما فقط تغییرات سمت کلاینت (Flutter) را توضیح می‌دهد؛ نه کاری که روی سرور انجام شده.

سه تفاوت بنیادی PocketBase و Supabase که تمام تغییرات ما را توضیح می‌دهند

موضوعPocketBase (قدیم)Supabase (جدید)
آدرس API الگوی collections/<نام>/records الگوی REST استاندارد rest/v1/<نام‌جدول>
ساختار پاسخ لیست‌ها شیء صفحه‌بندی‌شده: { "items": [...], "totalItems": n } آرایه ساده: [ {...}, {...} ]
فیلتر کردن پارامتر filter با سینتکس popularity="Hotest" پارامتر کوئری با سینتکس PostgREST: popularity=eq.Hotest
فایل‌ها و تصاویر نام فایل در دیتابیس ذخیره می‌شد و سمت کلاینت URL ساخته می‌شد: /api/files/{collectionId}/{id}/{file} URL کاملِ عمومیِ تصویر مستقیماً در دیتابیس ذخیره شده است — نیازی به ساخت URL در مدل‌ها نیست
احراز هویت یوزرنیم/پسورد با auth-with-password Supabase Auth با ایمیل/پسورد (ما یوزرنیم را به ایمیل ساختگی تبدیل می‌کنیم — بخش ۴)
کلید API لازم نبود هدر apikey در تمام درخواست‌ها الزامی است
💡 چرا مهاجرت انجام شد؟
PocketBase نمونهٔ آموزشی رایگان و اشتراکی (startflutter.ir) بود که در کنترل ما نیست؛ Stability و مالکیت داده‌ها تضمین نمی‌شد. Supabase سلف‌هاست روی سرور شخصی اجرا می‌شود: PostgreSQL واقعی، RLS (امنیت سطح ردیف)، Storage با لینک عمومی و سیستم احراز هویت استاندارد. مهم‌تر اینکه معماری کلاینت (UI، Bloc، Repository، DI) دست‌نخورده ماند — فقط لایه Datasource و Model و تنظیمات Dio عوض شد. این دقیقاً همان چیزی است که معماری لایه‌ای به ما قول می‌داد!

خوشبختانه چه چیزهایی هیچ تغییری نکردند؟

  • تمام صفحه‌های UI (Home، Category، ProductDetail، Login، Register، Profile، Card و…)
  • تمام Blocها و Eventها و Stateها
  • تمام Repositoryها (به‌جز دیتاسورس‌هایی که صدا می‌زنند)
  • سبد خرید محلی با Hive — کاملاً محلی بود و ربطی به بک‌اند ندارد
  • پرداخت زرین‌پال — مستقیم با درگاه زرین‌پال صحبت می‌کند
  • فایل auth_manager.dart — همان saveToken / saveId / readAuth قبلی
  • فایل di.dart — همان ثبت‌نام‌های GetIt قبلی

یعنی اگر ویدیوهای UI و Bloc و Repository را دیده‌اید، هیچ‌کدام باید دوباره دیده نشوند؛ فقط ویدیوهای مربوط به Datasource و Model و احراز هویت نیاز به «ترجمه» دارند که این سند همان ترجمه است.

۳) تنظیمات اتصال: فایل dio_provider.dart

این فایل نقطهٔ شروع همهٔ درخواست‌های شبکه است. دو چیز عوض شد: BaseURL و هدرها.

قدیم PocketBase

class DioProvider {
  static Dio createDio() {
    Dio dio = Dio(BaseOptions(
        baseUrl: 'https://startflutter.ir/api/',
        headers: {
          'Content-Type': 'application/json',
          'Authorization': 'Bearer ${AuthManager.readAuth()}'
        }));
    return dio;
  }

  static Dio createDioWithoutHeader() {
    Dio dio = Dio(BaseOptions(
      baseUrl: 'https://startflutter.ir/api/',
    ));
    return dio;
  }
}

جدید Supabase

class SupabaseConfig {
  static const String baseUrl = 'https://api.expertflutter.pro';
  static const String anonKey = 'eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...'; // کلید anon کامل در کد پروژه
}

class DioProvider {
  static Dio createDio() {
    final token = AuthManager.readAuth();
    final headers = <String, dynamic>{
      'Content-Type': 'application/json',
      'apikey': SupabaseConfig.anonKey,      // ① اجباری در تمام درخواست‌ها
    };
    if (token.isNotEmpty) {
      headers['Authorization'] = 'Bearer $token'; // ② فقط وقتی لاگین است
    }
    Dio dio = Dio(BaseOptions(baseUrl: SupabaseConfig.baseUrl, headers: headers));
    dio.interceptors.add(InterceptorsWrapper(
      onRequest: (options, handler) {
        options.headers['apikey'] = SupabaseConfig.anonKey;
        final t = AuthManager.readAuth();
        if (t.isNotEmpty) {
          options.headers['Authorization'] = 'Bearer $t';
        } else {
          options.headers.remove('Authorization'); // ③ هرگز هدر خالی نفرست
        }
        return handler.next(options);
      },
    ));
    return dio;
  }

  static Dio createDioWithoutHeader() {
    return Dio(BaseOptions(
      baseUrl: SupabaseConfig.baseUrl,
      headers: {
        'Content-Type': 'application/json',
        'apikey': SupabaseConfig.anonKey, // ④ این متد هم حالا apikey لازم دارد
      },
    ));
  }
}
💡 چرا این تغییرات؟
① هدر apikey: Supabase بدون هدر apikey درخواست را با خطای 401 رد می‌کند — حتی برای خواندن داده‌های عمومی مثل لیست محصولات. این کلید همان «anon key» است و عمومی بودنش امن است.
② و ③ اینترسپتور توکن پویا: در نسخهٔ قدیم، هدر Authorization همیشه ارسال می‌شد — حتی وقتی کاربر لاگین نبود و مقدارش رشتهٔ خالی بود (Bearer ). PocketBase این را نادیده می‌گرفت، اما Supabase با خطای PGRST301: Empty JWT is sent in Authorization header جواب می‌دهد! اینترسپتور تضمین می‌کند توکن همیشه تازه از AuthManager خوانده شود و اگر خالی بود، اصلاً هدر ارسال نشود.
④ createDioWithoutHeader: این متد برای صفحات ثبت‌نام/ورود است که توکن نداریم — اما چون apikey اجباری است، حالا آن را هم می‌فرستد. «بدون هدر» حالا یعنی «بدون Authorization» نه «بدون apikey».
⚠️ نکته اسلش (Slash)
در قدیم baseUrl به /api/ ختم می‌شد و مسیرها بدون اسلش اول نوشته می‌شدند ('collections/...'). در جدید baseUrl بدون اسلش آخر است و مسیرها با اسلش اول نوشته می‌شوند: 'rest/v1/products'. اگر اسلش را جا بیندازید، Dio مسیر را به دامنهٔ روت چسبانده و خطای 404 می‌گیرید.

۴) احراز هویت: ثبت‌نام و ورود با Supabase Auth

بزرگ‌ترین تغییر منطقی پروژه اینجاست. PocketBase با «یوزرنیم و پسورد» کار می‌کرد؛ Supabase Auth با «ایمیل و پسورد». برای اینکه UI و تجربهٔ کاربر دقیقاً همان بماند (کاربر فقط یوزرنیم وارد می‌کند)، ما یوزرنیم را به یک ایمیل ساختگی تبدیل می‌کنیم.

۴.۱) نگاشت یوزرنیم به ایمیل

username = "amirahmad"
        ↓ (ساخت سمت کلاینت)
email    = "amirahmad@appleshop.local"
💡 چرا appleshop.local؟
.local یک پسوند غیر اینترنتی است؛ یعنی «این یک ایمیل واقعی نیست». چون تأیید ایمیل (Email Confirmation) روی سرور خاموش است، هیچ ایمیلی ارسال نمی‌شود و این صرفاً یک شناسه یکتا برای Supabase Auth است. کاربر هرگز این ایمیل را نمی‌بیند — فقط یوزرنیم خودش را وارد می‌کند مثل قبل.

⚠️ دقت کنید apple_shop.local (با آندرلاین) نامعتبر است و سرور با خطای Unable to validate email address رد می‌کند — حتماً appleshop.local بنویسید.

۴.۲) جدول مسیرهای احراز هویت

عملیاتقدیم (PocketBase)جدید (Supabase)
ثبت‌نام POST collections/users/records
بدنه: {username, name, password, passwordConfirm}		 POST auth/v1/signup
بدنه: {email, password, data:{username, name}}
ورود POST collections/users/auth-with-password
بدنه: {identity, password}		 POST auth/v1/token?grant_type=password
بدنه: {email, password}

۴.۳) تفاوت ساختار پاسخ

// قدیم: PocketBase
{
  "token":  "eyJ...",
  "record": { "id": "o2puw73n1hpsrwd", "username": "amirahmad", ... }
}

// جدید: Supabase
{
  "access_token": "eyJ...",
  "user":       { "id": "a6e7b52b-957a-...", "email": "amirahmad@appleshop.local", ... }
}

پس در کد: response.data['token'] ← response.data['access_token'] و response.data['record']['id'] ← response.data['user']['id']. این مقدارها همان‌طور که قبل رفتند داخل AuthManager.saveToken() و AuthManager.saveId() ذخیره می‌شوند — AuthManager هیچ تغییری نکرد.

۴.۴) کد جدید ثبت‌نام (register)

Future<void> register(String username, String password, String passwordConfirm) async {
  try {
    if (password != passwordConfirm) {
      throw ApiException(400, 'رمز عبور و تکرار آن یکسان نیست');
    }
    final response = await _dio.post('auth/v1/signup', data: {
      'email': '$username@appleshop.local',
      'password': password,
      'data': {'username': username, 'name': username},  // metadata کاربر
    });
    if (response.statusCode == 200 || response.statusCode == 201) {
      final accessToken = response.data?['access_token'];
      final userId      = response.data?['user']?['id'];
      if (accessToken != null && userId != null) {
        AuthManager.saveId(userId);        // ثبت‌نام + ورود همزمان
        AuthManager.saveToken(accessToken);
        return;
      }
      await login(username, password); // اگر سشن برنگشت، لاگین کن
    }
  } on DioError catch (ex) { ... }
}
💡 سه نکته درباره کد بالا
۱) passwordConfirm: PocketBase خودش تطابق دو رمز را چک می‌کرد؛ Supabase فقط یک password می‌گیرد، پس تطابق را خودمان چک می‌کنیم.
۲) کلید data: یوزرنیم واقعی کاربر داخل metadata (کلید data) ذخیره می‌شود تا بعداً در جدول users قابل نمایش باشد.
۳) ثبت‌نام = ورود: چون تأیید ایمیل خاموش است، پاسخ signup بلافاصله شامل access_token است؛ یعنی کاربر بعد از ثبت‌نام، همان‌ لحظه لاگین‌شده است — همان رفتار قدیم!

۴.۵) کد جدید ورود (login)

Future<String> login(String username, String password) async {
  try {
    var response = await _dio.post('auth/v1/token?grant_type=password', data: {
      'email': '$username@appleshop.local',
      'password': password,
    });
    if (response.statusCode == 200) {
      final token  = response.data?['access_token'] as String?;
      final userId = response.data?['user']?['id'] as String?;
      if (token == null || userId == null) {
        throw ApiException(0, 'خطایی در ورود پیش آمده!');
      }
      AuthManager.saveId(userId);
      AuthManager.saveToken(token);
      return token;
    }
  } on DioError catch (ex) { ... }
  return '';
}
⚠️ نکتهٔ مهم درباره کاربران قدیمی (حتماً به دانشجوها بگویید)
رمزهای عبور کاربران PocketBase با الگوریتم bcrypt ذخیره شده بودند و قابل انتقال به Supabase Auth نیستند (دسترسی به رمزهای خام نداریم — و این خوب است!). بنابراین: همهٔ ۱۳۶۸ کاربر قدیمی با همان یوزرنیم و کامنت‌هایشان در دیتابیس جدید موجودند، اما برای ورود باید یک‌بار دوباره ثبت‌نام کنند با همان یوزرنیم قبلی. اگر یوزرنیم تکراری وارد شود خطای «قبلا ثبت شده» می‌گیرند. این رفتار طبیعی مهاجرت است، نه باگ!
